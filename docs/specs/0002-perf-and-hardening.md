# 0002 — Производительность и версионирование

- Статус: `in-progress`
- Дата: 2026-08-21
- Модуль: `kv04.diary`, инфраструктура репозитория

## Зачем

Приоритет продукта — мгновенный отклик при любом объёме контента и числе
пользователей. Замеры показали, что упирается не в объём данных (12 заметок),
а в накладные расходы на каждый запрос. Плюс проект не имел версионирования
при `autoUpload=Always`: любая правка уезжала на прод без возможности отката.

## Решение

**Версионирование.** `git init`, ветка `main`, remote
`git@github.com:polurama152/kv04_ru.git`. Из репозитория исключены ядро
Bitrix (5.7 ГБ), `upload/`, дампы, `cgi-bin/` (28 МБ бинарников прежнего
хостинга) и всё, что содержит пароли: `.settings.php`, `dbconn.php`.
`.gitattributes` держит LF — сервер Linux.

**`Installer::ensure()`.** Вызывался дважды за запрос (`index.php` и
`executeComponent()` обоих компонентов) и каждый раз выполнял ~10 запросов
старым API плюс два безусловных `INSERT INTO b_option`. Каждый показ главной,
включая гостевой, писал в базу; под конкурентной нагрузкой это упёрлось бы в
блокировку двух одних и тех же строк.

- статический флаг `$ensured` — повторный вызов в том же запросе бесплатен;
- опция `schema_version` — выход без единого запроса, если схема применена;
- `setOption()` сверяет значение перед записью;
- `ensure(true)` — принудительное переприменение;
- идентификаторы HL и инфоблока проверяются отдельно, поэтому ручное удаление
  сущностей приводит к повторному созданию, а не к тихому пропуску.

Вызовы в компонентах оставлены: модуль должен быть самодостаточным у клиента
Маркетплейса, а стоимость повторного вызова теперь нулевая.

## Вне скоупа

N+1 в `NoteService::list()`, счётчик `ipfail_*` в `b_option`,
локальный highlight.js, переезд с shared-хостинга — вынесено в долг ниже.

## Контракт

Новая опция модуля `kv04.diary`: `schema_version` (строка, текущее значение
`1`). Поднимать `Installer::SCHEMA_VERSION` при изменении структуры HL или
инфоблока — это заставит `ensure()` один раз переприменить схему.

Сигнатура: `Installer::ensure(bool $force = false): void`. Поведение при
`$force = false` и применённой схеме — no-op.

Сняты на сервере (`php8.4`, боевая база, `curl` с `127.0.0.1` — без сети).

### Из чего складывается отклик

Замерено через веб-SAPI (mod_php с opcache), а не CLI — цифры боевые.

| Слой | Стоимость | Чем убирается |
|------|-----------|---------------|
| nginx → Apache → mod_php, до первой строки PHP | **29–32 мс** | только сменой хостинга на nginx + PHP-FPM |
| `prolog_before` ядра Bitrix | **25–35 мс** | только отказом от Bitrix на этом запросе |
| Всё остальное: компоненты, `NoteService`, шаблон | ≈40 мс | оптимизацией нашего кода |

Отдельно проверено: «облегчённый» пролог с `NO_KEEP_STATISTIC`,
`NO_AGENT_CHECK`, `DisableEventsCheck`, `PUBLIC_AJAX_MODE` и
`BX_SKIP_SESSION_TERMINATE` даёт **25–29 мс против 25–35 мс** — в пределах
погрешности, выигрыша по медиане нет. Смысл у `NO_AGENT_CHECK` остаётся
только как страховка хвоста: без него на случайный запрос может выпасть
прогон агентов Bitrix.

Не узкие места: TLS-хендшейк сервера 6–10 мс, MySQL 0.03 мс/запрос,
`innodb_buffer_pool` 8 ГБ.

## Ловушка, на которой уже обожглись

Быстрый путь `Installer::ensure()` убрал не только запросы, но и побочный
эффект: раньше метод на каждом запросе вызывал `Loader::includeModule('iblock')`,
и `NoteService` молча этим пользовался. После оптимизации лента залогиненного
пользователя падала с `Class "CIBlockElement" not found` — то есть HTTP 500 и
«Нет связи» в интерфейсе. Гостевую страницу это не задевало, поэтому проверка
главной ничего не показала.

Барьер `NoteService::requireIblock()` теперь стоит **первой строкой каждого
публичного метода**. Внутри `iblockId()` его недостаточно: PHP резолвит класс
`CIBlockElement` раньше, чем вычисляет аргументы вызова, поэтому
`CIBlockElement::GetList(..., self::iblockId(), ...)` падал бы до срабатывания
проверки.

Вывод на будущее: убирая вызов из горячего пути, проверять не только время, но
и то, что этот вызов делал попутно. И проверять оба состояния — гостя и
залогиненного, — они идут разными ветками кода.

## Долг

**Безопасность, срочно.**

- ~~`/bitrix/backup/*.sql` и `*.tar.gz` скачиваются публично~~ — **закрыто
  2026-08-21.** Причина: восстановление 2026-06-27 распаковало архив прямо в
  `bitrix/backup/`, и корневой `.htaccess` из архива лёг поверх штатного
  `Deny from All`. Архивы удалены, защита восстановлена, проверено канарейкой.
- `PinService::create()` не проверяет блокировку по IP и отвечает «Такой пин
  занят» — это оракул существования PIN без лимита попыток. 10 000 запросов
  перебирают всё пространство и обходят защиту `login()`.
- `PinService::registerPinFail()` (`pinservice.php`) не вызывается ниоткуда.
  Полей `UF_FAILS` / `UF_LOCKED_UNTIL` это не наполняет, поэтому обещанная
  спекой `0001` блокировка «3 попытки на PIN» не работает. В текущей модели
  она и не может работать: неверный PIN не совпадает ни с одной записью.
- Успешный вход сбрасывает счётчик IP — владелец своего дневника перебирает
  чужие по два предположения за цикл.
- Публично доступны отладочные скрипты в корне: `test.php`, `check_tables.php`,
  `check_encoding.php`, `bitrix_test.php`, `enum_test.php`, `index_.php`,
  `bitrixsetup.php`.
- `session.use_strict_mode = 0` на хостинге — возможна фиксация сессии.

**Производительность.**

- `NoteService::list()` — N+1: `GetProperty` на каждую заметку плюс
  `CFile::GetFileArray` на каждый файл, до ~500 запросов на полную ленту.
- `ipfail_*` в `b_option` растёт неограниченно, а Bitrix грузит все опции
  модуля в память при первом `Option::get`.
- ~~`location.reload()` после сохранения~~ — **убрано 2026-08-21.** Сервер
  отдаёт готовый элемент (`NoteService::get()`), фронт дорисовывает его сам;
  правка подставляет пришедший санитизированный HTML вместо textarea.
  Компонент больше не перечитывает всю ленту после `add`. Перезагрузка
  осталась только на выходе из дневника, где она уместна.
- highlight.js с cdnjs блокирующим `<script>` — лишние DNS + TLS к третьему домену.
- Статику отдаёт Apache, а не nginx: 20 мс вместо ~1 мс. Нет HTTP/2.
- Сессии в файлах — блокировка сериализует параллельные запросы пользователя.
- ~~3.4 ГБ мусора в document root~~ — **вычищено 2026-08-21**, освобождено
  3.3 ГБ и 131 тыс. inode. Общий массив хостинга по-прежнему занят на 98% —
  это не наша квота, а риск площадки.

**Инфраструктура.** Shared-хостинг Beget — потолок для цели «мгновенный
отклик». Redis и Memcached недоступны, кэш Bitrix файловый. Следующий шаг —
VPS 4 vCPU / 8 ГБ / NVMe: nginx + PHP-FPM без Apache, Redis под сессии и кэш,
HTTP/2 и HTTP/3. Ожидаемо 120 мс → 25–40 мс.
